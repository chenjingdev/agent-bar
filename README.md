# agent-bar

A local macOS menu bar app for monitoring **Codex and Claude Code subscription limits across multiple accounts**.

Download the app from [GitHub Releases](https://github.com/chenjingdev/agent-bar/releases/latest). The prebuilt app supports Apple Silicon Macs running macOS 14 or later. It is ad-hoc signed and is not notarized by Apple; macOS may require allowing the first launch in System Settings › Privacy & Security. Extract the ZIP and place `AgentBar.app` in Applications. The official provider CLIs are still required.

## Accounts and menu bar

**Settings › Menu Bar** is the editor for every menu bar group. Groups use clickable tabs, styles use illustrated buttons, and limits use direct selection buttons; the selected option is highlighted. A group is one clickable menu bar item; its ordered usage lines can mix Claude and Codex accounts and limits freely.

Opening Settings from a menu bar group's popover selects that exact group, including when several groups use the same account. The selected group remains selected while switching settings tabs or reopening the window within the running app. Empty menu bar items open their own group's editor directly.

- **Add Group** creates another independent group, without a fixed group-count limit. **Show** hides a group without deleting its configuration. Delete removes only that display group, never its accounts. Drag an AgentBar badge onto another badge, or drag the group buttons in Settings, to reorder without a modifier key. The app reuses its existing menu bar positions and saves the new group-to-position mapping. Native ⌘-drag remains available for positioning items among other apps.
- **Three fixed slots** show existing lines or a centered **+** in each empty slot. Clicking **+** adds an editable line in that slot, initially using the last account in the group (or the first available account) and its weekly limit. Each compact line keeps its drag handle, account, direct limit buttons, and remove button on one row. Dropping onto an occupied slot swaps the two lines. To put a line in another group, add it there and remove the old line. A common badge can appear once at the left of the group with its own text and color. Bar and gauge colors follow each account. The group name labels the group only. The same account can appear in several lines or groups. Missing data remains `--` for the selected limit, never a substitute limit or a false zero.
- Each group independently chooses its style, common badge visibility, percentage visibility and **up to three usage lines in one column**. Full groups cannot receive another line once all three slots are occupied; there are no overflow columns. Multi Bar always shows its equal-thickness bars and optionally shows one large percentage for the line selected with its `%` button; dragging that line keeps the selection, and deleting it falls back to the first line.
- Four styles are available: **Multi Bar** (stacked bars with one full-size representative percentage), **Ring Gauge** (a high-contrast progress ring with a full-size percentage beside it), **Capsule Fill** (up to three capsules matching the Multi Bar width, stacked in one column), and **Text Only**. Text Only has no line limit and lays every percentage out horizontally in configured order, without labels. Remove values until three remain before switching an unlimited Text Only group to another style. Ring Gauge always edits, refreshes, and displays only the first configured usage line. The old Name Badge style maps to Multi Bar. Changes appear immediately in the actual menu bar. Usage at 90% or more turns the gauge red.
- **Settings › Accounts** manages login, reconnect and deletion. Drag the handle beside an account to reorder the list; every usage-line account picker immediately uses that saved order without changing its selected account. All accounts can be moved. New accounts append to the list, and the order survives restart. Use a group’s Show switch or remove a usage line to control what is displayed and refreshed. **Add Account** opens an agent picker populated from the supported providers. Every account has the same two menu actions: Reconnect and Delete. Login email, provider and organization are visible directly below each account name. Under a Claude account a line says whether the account is **In Claude Code**, **Ready for Claude Code** or **Not set up for Claude Code**; the last has the **Sign In…** button that makes it ready (see **Use in Claude Code** below). Older rows that followed a CLI login require a separate AgentBar sign-in; their layout selections are preserved. Deleted accounts stay removed after restart. New accounts receive a distinct palette color when possible and are initially added to their own group.
- **Account names come from the account itself**; AgentBar has no rename. A Claude account shows its profile's display name (claude.ai Settings › Profile, "What should Claude call you?", else the full name), read from `api/oauth/profile` on every usage refresh, together with the organization name. A Codex account shows the name on its ChatGPT login: the `name` claim of the ID token the official CLI saves in the account's `auth.json`, read on every refresh; OpenAI issues a new ID token when Codex renews the login, so a name changed in ChatGPT appears after that renewal. An account without a name shows its login email, then the provider. Accounts that share a name are told apart by the login email, then the provider where it is not already shown, then the organization, each added only where it differs. Names typed in earlier versions are no longer read; the next save of `accounts.json` drops them.
- **Settings › General** controls the refresh interval and the theme (System, Light or Dark). The theme applies to AgentBar's windows and popovers; menu bar items keep following the menu bar. Clicking a group opens a popover with one tab per account, even if that account has several lines. An empty group's `+` opens the Menu Bar editor. Reopening AgentBar opens Settings, including when every group is hidden.
- A non-blocking notice appears when AgentBar's combined width exceeds 40% of its display width; this is a heuristic, not a measurement of remaining menu bar space.
- **Every account is monitored independently** using its own AgentBar credential directory. A new installation starts with no accounts; use Add Account to sign in separately. AgentBar never imports or follows the login used by Claude, Codex, or another app. The one exception is **Use in Claude Code** (see [How authentication and usage work](#how-authentication-and-usage-work)): it reads which account Claude Code's default login belongs to and, only when you press it, signs one of your Claude accounts in there and keeps the login it replaces for that login's own account, if AgentBar has it. Each account first signs in once in the browser from **Settings › Accounts**; usage reading never uses these logins. Legacy rows without an AgentBar credential show Sign-in required and are excluded from polling until reconnected.

Dragging accounts, groups, and usage lines lifts a translucent copy with a shadow. The destination is previewed before dropping; dropping outside the list returns the item to its original position. Account and group moves insert at the destination, while usage lines swap occupied slots or move into empty slots.

Existing account-based `display-v2.json` preferences remain readable. The first group edit saves explicit ordered layouts and first backs up the previous file as `display-before-layouts-<UUID>.json`. Account visibility and colors are retained.

An item-based `display-v1.json` from the first multi-account version is no longer read. AgentBar leaves the file untouched.

## Requirements

- macOS 14 or later; Swift 6.2 or later to build.
- `/usr/bin/python3` for isolated CLI process-group startup and cleanup.
- Official Codex and/or Claude Code CLI installed. Homebrew installations are preferred over user launch wrappers.
- Claude Code 2.1.309 or newer for **Use in Claude Code**. With an older version, or one whose version cannot be read, its button and **Sign In…** in Settings › Accounts are disabled and say why. There is no upper limit.
- A supported subscription login for every account to monitor. API keys and API billing usage are outside this app's scope.

The implementation was developed against Codex CLI 0.154.0 and Claude Code 2.1.263, and **Use in Claude Code** against Claude Code 2.1.312. Provider interfaces can change with CLI releases.

## How authentication and usage work

**Codex:** AgentBar launches the official `codex app-server` in a separate `CODEX_HOME` for each managed account. It uses managed ChatGPT OAuth login, `account/read`, and `account/rateLimits/read`. The same read reports the account's usage limit resets and remaining credits (see below). Managed accounts use the CLI's file credential storage in a private directory. Existing CLI launch wrappers and routing configuration are not modified.

**Claude:** A private per-login browser-opener helper captures the CLI's automatic OAuth URL before opening it in the selected browser. The URL is validated and immediately removed from disk. The CLI keeps ownership of its PKCE state, local callback, and initial token exchange. AgentBar launches `claude auth login --claudeai` with a separate `CLAUDE_CONFIG_DIR`. It verifies the JSON login status during login and uses that directory's OAuth credential to query Anthropic's usage endpoint. Usage reads require an explicit account directory and prefer its private credential file. Existing account-owned Keychain entries can be read without authorization dialogs. There is no fallback to the external CLI directory, inherited authentication environment, or shared default Keychain entry.

**Usage limit resets and credits:** Below the limits, an account's popover shows how many usage limit resets it can still use, one row per coupon with its title and expiry, and its credits. For Codex that is the credit balance: an account Codex reports as having no credits shows 0, and a value Codex did not report shows `--`. For Claude it is what Claude Code's `/usage` screen reads from the same usage reply: one-time dollar credits with the amount used and their expiry (titled by their label, or "Credit"), extra usage spent this month against its monthly limit (or Off), and any prepaid usage credit balance. Each coupon the provider can use now has its own **Use…** button. After a confirmation in the popover it uses that coupon, which cannot be undone; the backend never picks one. The confirmation shows how much of each limit the coupon resets is used now and warns when all of them are under half used, since the reset would then give back little. Claude names those limits in each grant's `clears` (Claude Code calls `seven_day_overage_included` the Fable limit); for Codex they are the 5-hour and weekly limits. A coupon within three days of expiring shows its expiry in orange, and an expired coupon loses its button. AgentBar reads the resets again first and sends nothing if the coupon no longer qualifies. For Codex the coupon is a credit: it must still be listed as `available`, and `account/rateLimitResetCredit/consume` names it with `creditId` and a fresh idempotency key. For Claude the coupon is a grant of the reset program, which the usage request reads by adding `cedar_ember=1` (falling back to the plain request if that flag is refused). Claude takes grants only in its own order, so only the grant it names next has a button; the others say Claude uses another reset first. Using it reads the program again (`cedar_ember=1&skip_spend=1`) and, if that grant is still next, claims it through `/api/organizations/<organization>/reset_rate_limits`, as Claude Code 2.1.295 does. Claude requests send `User-Agent: claude-cli/<installed version> (external, cli)`, the header Claude Code itself sends to these endpoints, because Claude decides eligibility from the CLI version and surface in it. After an attempt the account is read again at once, skipping the usage cache and the refresh cooldown but not a rate-limit backoff. Every attempt is recorded in `logs/limit-resets.log`, which **Open Log** beside the attempt's result opens.

Expired Claude credentials owned by AgentBar are renewed with the existing refresh token before loading usage. Refreshes for the same credential file share one exchange, rotated tokens are saved atomically, and revoked credentials still require Reconnect. External CLI credentials are never renewed to read usage. No model prompts are sent to refresh or verify authentication.

The old shared Claude status-line bridge is not used by the multi-account reader because its samples do not identify their owning account. The optional legacy script remains in the repository but is not installed or reconfigured by this app.

Sign-in opens the usual default browser. For Codex, AgentBar adds `prompt=login` to show saved accounts and **Sign in with another account**, preserving the original encoded PKCE, state and callback parameters. Claude uses its official approval page; **Switch account** there changes the Claude website login as well. AgentBar never forces a website logout. Completing browser sign-in still writes only to a separate AgentBar directory: the account's credential directory, or its `lend/` folder for **Use in Claude Code**.

**Use Private Window Instead** is available during a sign-in from Settings › Accounts if a separate browser session is needed (the sign-in for **Use in Claude Code**, **Sign In…** on an account's line, opens only the usual browser). The private window is an incognito window in a temporary profile in a supported Chromium browser (Chrome, Edge, Brave or Chromium), with [ASWebAuthenticationSession ephemeral browsing](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession/prefersephemeralwebbrowsersession) as a fallback. Only an owned private session is closed on completion/cancellation; tabs in the usual browser remain under the user's control. Cancel in AgentBar to stop a normal-browser sign-in. Late private-window callbacks cannot cancel a later attempt.

The browser/account boundary follows the patterns reviewed in [Orca's Claude login session](https://github.com/stablyai/orca/blob/4aaa6c7fb48513e1e1e037eb648f0ab81826aeb3/src/main/claude-accounts/claude-login-session.ts) and [OpenCodex's ChatGPT OAuth flow](https://github.com/lidge-jun/opencodex/blob/7c625fc9755c9824653ab944190e243091a2c85c/src/oauth/chatgpt.ts). Like Orca, Claude launches for an AgentBar account explicitly set both `CLAUDE_CONFIG_DIR` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` to the account-owned directory; only **Use in Claude Code** runs `claude` without them, to read its version and to sign in Claude Code's default login.

Completing a Claude connection saves its credential into the account's private file before reporting success. macOS may request Keychain access at that point. Periodic usage refreshes never read a Keychain secret; for **Use in Claude Code** they only ask `/usr/bin/security` whether Claude Code's default login item exists and whether each Claude account has a saved sign-in, without reading a secret. If access is denied, AgentBar reports the connection failure instead of registering an account it cannot read.

**Use in Claude Code:** The header of each Claude account's popover has a **Use in Claude Code** button beside the provider name. One press changes Claude Code's default login, the one `claude` uses when it starts without `CLAUDE_CONFIG_DIR` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` (`~/.claude.json` and the `Claude Code-credentials` Keychain item), to that account. Open sessions switch within 30 s and Remote Control disconnects; the result line under the header says so and offers **Open Log**. The account Claude Code uses shows **In Claude Code** instead of the button. That mark follows Claude Code's actual login (the account and organization in `~/.claude.json`, and whether the Keychain item exists), so a change made in a terminal shows too, while an account AgentBar does not have, or a signed-out Claude Code, marks no window. While a Claude account exists, each usage refresh runs `claude --version` and reads that login, and opening a popover reads the login again. The button is hidden when no `claude` program is found, and in a development run started with `AGENTBAR_DATA_DIR` or `AGENTBAR_DEFAULTS_SUITE`, which never reads or changes Claude Code's login. It is disabled with the reason while AgentBar is still checking Claude Code, when Claude Code is older than 2.1.309 or its version cannot be read, when the account shows Sign-in required, and when AgentBar cannot tell the account's login apart from another (Reconnect fixes that). While a switch runs, every **Use in Claude Code** button is disabled, and the account being switched to and the one Claude Code had cannot be reconnected or deleted; at launch, until AgentBar has checked for a switch that was cut short, no Claude account can be reconnected or deleted. Each account's saved sign-in for this lives in its own folder, `lend/<account UUID>/`, apart from its usage login, so a switch never touches the usage login or the usage the popover shows. The popover button never opens a browser. An account signs in once, from **Settings › Accounts**: each Claude account's line there says **In Claude Code**, **Ready for Claude Code** (a sign-in is saved) or **Not set up for Claude Code**, and the last has a **Sign In…** button. It opens the usual browser, waits up to 5 minutes (**Cancel** stops it) and saves the login in that account's folder; a sign-in as a different account than the line's is discarded, and a failure is said on the line, beside **Open Log**. While nothing is saved for an account, its popover shows **Set Up in Settings…**, which opens Settings › Accounts, in place of **Use in Claude Code**. **Sign In…** is disabled for the reasons that disable the switch button, except Sign-in required (the usage login is separate), and while a switch or another sign-in runs; the account being signed in cannot be reconnected or deleted. A saved login that Claude refuses when a switch uses it has expired: the switch changes nothing, the login is removed, and the result line asks for a new sign-in in Settings › Accounts, where the line then offers **Sign In…** again. Later switches to a saved account need no browser as long as its login is kept: a `/login` or `/logout` in Claude Code itself, which AgentBar does not prevent, loses the login Claude Code had, and that account signs in again in Settings.

A switch never writes Claude Code's login entries itself. AgentBar runs the official `claude auth login --claudeai` with the saved refresh token and scopes in `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` and `CLAUDE_CODE_OAUTH_SCOPES`, which reach Claude Code only through the environment of that one command. The command gets AgentBar's minimal environment and, for the default login, no folder variables. A refresh token works once, so the saved copy is used up and removed. AgentBar then reads the default login again and counts the switch only if it now holds the chosen account's login under a new token. The login Claude Code had before is kept in memory only and, once its token has left the default login, saved into its own account's folder the same way (up to three tries, 3 s and 6 s apart), so switching back needs no browser. If Claude Code is signed in to an account AgentBar does not have, the chosen account's window asks first (**Cancel** or **Switch**), because the switch removes that login from Claude Code. A saved login that Claude refuses (`invalid_grant`, or a 400 or 401 status in the command's output, worded as Claude Code 2.1.312 prints it) is removed, and the switch stops there. Any other failure, such as a network error or a time-out, stops the switch and keeps the saved login for the next try. When the previous login cannot be saved, the switch stands and the result line says that account needs to sign in again in Settings › Accounts. Before the default login is first changed, AgentBar records the target, the previous account and the stage, without any token, in `claude-code-switch.json`, and removes the record when the switch ends. If AgentBar quits meanwhile, the next launch finishes the clean-up or drops the record and says so on the target account's window, and an account whose login was only in memory needs to sign in again in Settings › Accounts. A sign-in from Settings never reads or writes the default login and needs no such record: whatever one cut short leaves in the account's folder is checked, and removed if it cannot be used, the next time the folder is looked at. AgentBar reads Claude Code's default login item and the saved sign-ins, and removes saved sign-ins, only through `/usr/bin/security`, never the Security API, so a switch asks for no Keychain authorization. Tokens are read only while a switch runs and while a sign-in from Settings is checked, and are never shown or logged. For this feature AgentBar writes no token to a file: it creates no `.credentials.json` in the saved folder, and the token stays in the Keychain item Claude Code makes for that folder. Deleting a Claude account also removes its saved sign-in from this Mac and checks that it is gone. Claude Code's own login is left alone, even when it belongs to that account. If a switch or a sign-in from Settings is running, the account disappears at once and its saved sign-in is removed when it ends. If removing it fails, Settings › Accounts shows why and offers **Retry Pending Cleanup**.

## Data, refresh, and privacy

Account data lives under `~/.agentbar/multi-account-v1/`:

- `accounts.json`: versioned account metadata, representative selections, and pending cleanup records. No passwords or tokens.
- `display-v2.json`: account metadata and explicit groups with ordered account/limit lines, per-group styles, component toggles, visibility and row counts. Legacy v2 fields are retained for migration. No credentials. Layout backups and an unused `display-v1.json` may remain alongside it.
- `credentials/<UUID>/`: per-login CLI authentication/configuration directory. Its path remains fixed after login because Keychain storage may depend on it.
- `usage/<account UUID>/<credential UUID>/`: isolated usage cache and last-known-good snapshot.
- `lend/<account UUID>/`: the sign-in saved for **Use in Claude Code**, at most one folder per Claude account. Claude Code stores the login there (both folder variables name this folder), so its token lives in the Keychain item Claude Code names after the folder path and AgentBar creates no `.credentials.json` in it. Removed with the account.
- `claude-code-switch.json`: present only while a **Use in Claude Code** switch is changing Claude Code's login, or until the next launch after AgentBar quit during one: the target, the previous account and the stage. No tokens.
- `logs/limit-resets.log`: one JSON object per line for each usage limit reset attempt, sharing an attempt ID: what the popover showed, the provider's fresh reset status, the request (without its Authorization header), the reply or error, the result, and what the popover showed after the follow-up refresh. Refreshes add a `status` line only when what a provider reports about resets changes. Token-like values are redacted. The file moves to `limit-resets.log.1` after about 1 MB.
- `logs/claude-code-switch.log`: one JSON object per line for each **Use in Claude Code** switch and each **Sign In…** from Settings › Accounts, sharing an attempt ID: its start, each step (version check, current login, saved login, browser sign-in, hand-over, check, saving the previous login) with its outcome, and the result. The start and result lines of a sign-in carry `"operation": "prepare"`, and a sign-in only has the steps version check, saved login and browser sign-in. A switch cut short adds a recovery line at the next launch. Token-like values are redacted, and the output of Claude Code's commands is cleaned of the tokens used before it is logged. The file moves to `claude-code-switch.log.1` after about 1 MB. **Open Log** beside a switch's result, or beside the reason a sign-in failed, opens it.

Directories use mode `0700`; app-written files use `0600`. For managed Claude accounts, connecting copies the credential Claude Code saved in the Keychain into that account’s private `.credentials.json` once. Usage refreshes read and renew only this file, because the Keychain copy keeps the sign-in refresh token, which stops working after the first renewal. The file stays readable while the Mac is locked so refreshes continue. OAuth tokens stay in these private credential stores; they are never written to usage caches or app logs. Treat credential directories and local backups as private.

Provider detection checks only whether the official CLI executable is installed. Startup cleanup suppresses Keychain authorization UI. If an account's credential file is missing or can no longer be renewed, the account shows a sign-in-required state and retains available cached usage as stale. Routine identity checks read local account metadata without spawning Claude, and credentials are rechecked after each usage request to discard results from a changed login; the only Claude process AgentBar starts routinely is **Use in Claude Code**'s `claude --version`, once per refresh while a Claude account exists.

The existing refresh interval is preserved (60, 120, 300, or 600 seconds). Accounts unused by any visible group are excluded from both automatic and manual refresh. Legacy paused accounts stay paused until reenabled from a usage line. An account used by several groups is polled once per refresh. Selected limits keep polling even when they have no data so they can appear later. Showing an account again schedules its refresh while respecting retry cooldowns. Requests are serialized per provider. Changing the refresh interval applies immediately. Provider retry deadlines are preserved even if a response arrives after an account is hidden; manual refresh does not bypass a cooldown. Failures are isolated to the affected account.

Unknown usage is `--`, not `0%`. Old values retain their original timestamp and are marked stale. Existing global cache files are not imported into managed accounts. Legacy caches from externally signed-in CLI accounts are never read. Both usage providers and account sign-in launchers require an explicit account-owned directory.

No backend, telemetry, browser-cookie extraction, or session-log scanning is added. Authentication and usage requests go to the relevant provider through its CLI or usage endpoint.

## Automatic updates and releases

AgentBar uses [Sparkle](https://sparkle-project.org/) to check for updates hourly, download them, and install and relaunch automatically. Automatic updates are enabled by default. Settings › General shows the installed version, an automatic-update switch, and **Check for Updates…**. An automatic restart waits for an active account sign-in, Claude Code account switch or setup, or coupon redemption to finish.

Updates are fetched over HTTPS from the latest GitHub release's `appcast.xml`. Sparkle verifies the signed feed and the update archive against the public key embedded in the app before installing it. Account data and settings remain in their existing locations.

Versions before 0.3 do not contain an updater. Install a current release once to enable automatic updates afterward.

Every push to `main` runs the release workflow: tests, build, ad-hoc app signing, signed appcast generation, and publication of the app ZIP, checksums, and appcast as a GitHub release. Pull requests run validation without release credentials. The version is `VERSION` plus the full Git commit count, such as `0.3.51`; the same count is the bundle build number. A full Git history is required when building.

The repository's `SPARKLE_PRIVATE_KEY` Actions secret signs the feed and archive. Only the Sparkle public key belongs in `config/sparkle-public-key.txt`. The private key is also retained in this Mac's Keychain under the Sparkle account `dev.chenjing.agent-bar`. Keep it safe; replacing it prevents existing installations from trusting updates signed only with the replacement key.

## Build and install

```bash
swift test
./scripts/build-app.sh
```

To install, first quit the existing AgentBar, then run:

```bash
./scripts/build-app.sh --install
open ~/Applications/AgentBar.app
```

An ordinary update replaces only `~/Applications/AgentBar.app`. Accounts, login credentials, preferences, and usage data remain in their existing locations. The installer does not create historical app or account-data backups, and it leaves backups made by older installers untouched. Data migrations preserve only the specific settings files they change; for example, layout migration saves the previous display JSON.

The installer checks that all AgentBar instances are closed before building and again before replacement, including instances launched through a different path. Concurrent installations to the same destination are refused using an OS file lock, which is released when the installer exits. It verifies the source, staged, and installed app signatures. The previous app is held temporarily on the same filesystem and restored if replacement or verification fails; successful installation removes that temporary copy. If restoration itself fails, the previous app is retained at the recovery path printed by the installer.

For stable macOS Keychain authorization across local rebuilds, the script uses `AGENTBAR_CODE_SIGN_IDENTITY` when set, otherwise a recognized local code-signing identity already installed on this Mac, with ad-hoc signing only as a fallback. The local bundle is not notarized for public distribution. To return to an older release with a compatible data format, quit AgentBar and replace the app bundle; the existing accounts and preferences can remain in place. A release that changes a data format needs migration-specific recovery instructions and a targeted backup of the affected files. Older versions may not understand the newer format. Never restore over unrelated CLI or Keychain data.

## Validation

`python3 scripts/test_install.py` exercises app installation in temporary directories with fixture bundles and mocked system commands. It checks running-app preflight (also using a real native fixture process), concurrent installation with the real OS lock, signature and replacement failures, rollback, temporary-file cleanup, and preservation of existing user data without creating historical backups.

`swift test` covers mixed-provider line order and missing data, per-group display options, theme persistence and popover appearance, duplicate-account popover routing, more than four groups, hidden-account refresh suspension/resumption, CLI process-tree cleanup, account storage and permissions, representative persistence, cache isolation, Codex usage limit resets and credits, Claude Code login switching against a stand-in Claude Code and Keychain, unknown-versus-zero values, credential mismatches, delayed-result rejection, process cancellation/timeouts, and SwiftUI rendering.

An explicit installed-CLI probe can exercise Codex OAuth startup and cancellation **without opening a browser or signing in**:

```bash
AGENTBAR_LIVE_AUTH_PROBE=1 swift test --filter isolatedCodexLoginCancellation
```

Real OAuth completion, multiple-account usage, native UI interaction, using a usage limit reset (which spends a real reset), and signing in an account for Claude Code with **Sign In…** and switching Claude Code's real login with **Use in Claude Code** (which also switches open Claude Code sessions) are separate manual acceptance checks; `logs/limit-resets.log` and `logs/claude-code-switch.log` record each step. Passing unit tests or receiving an OAuth URL does not establish those results.

See [validation coverage and manual acceptance limits](docs/validation/multi-account/README.md).
